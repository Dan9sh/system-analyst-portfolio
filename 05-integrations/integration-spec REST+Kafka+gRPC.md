3. Входящие интеграции

### 3.1. REST-эндпоинты, которые мы отдаем
#### 3.1.1. Создание нового шаблона уведомлений
Метод и URL: POST api/v1/template  \
Назначение: Создать новый шаблон уведомлений
Тело запроса (пример):
```
{
   "data":{
	"name":"new template",
	“serviceId”:732982,
	“categoryId”:51413,
	"notification":{
		"smsNotification":"This is an FCM notification message!",
		"smsNotification": “This is an SMS notification message”
		"title":"FCM Message from zanachka",
		“channel”:[
			”push”,
			“sms”],
		“channelPriority”:3
	
      }
   }
}
```

Тело ответа (пример):
```
{
   "templateId":”3115sg34fr1_51”
}
```
Коды ошибок: \
201 – Шаблон успешно создан \
429 - Превышено ограничение на отправку для целевого адреса сообщения \
503 - Сервер перегружен
#### 3.1.2. Получение истории уведомлений

Метод и URL: GET api/v1/notification/history?user_id={user_id}&status=published&offset=0&limit=10 \
Назначение: Получить историю отправленных уведомлений по конкретному клиенту \
Тело запроса (пример):
- отсутствует

Тело ответа (пример):
```
{
"userId":”3115sg34fr1_51”,
"templateText_id":”3115sg34fr1_51”,
“kafkaMessId”:”51351”,
“message”:” Ваш код для входа: 482911”,
“dateOfCreate”:” 2026-09-01 09:00:00.000”,
“dateOfPublished”:” 2026-09-01 09:01:00.000”
}
```
Коды ошибок:
200 – Список получен \
403 – Нет прав для данного контента \
503 - Сервер перегружен

### 3.2. Kafka-топики, куда мы публикуем
#### 3.2.1. Топик: topic for FCM
Консюмер(ы) (чужой сервис): Адаптер для FCM
Ключ партиционирования: user_id
Логика продюсера:
1.	Сервис уведомлений вычитывает новое уведомление из топика уведомлений(основного или приоритетного);
2.	По user_id получает данные из системы пользователей;
3.	Подставляет текст в шаблон нужного уведомления
4.	Пишет в топик topic for FCM/APNs
